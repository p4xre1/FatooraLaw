# Environment configuration — every case, every fix

Everything the browser needs is inlined **at build time**. That single fact
explains almost every "I set the variables and it still says Supabase is not
configured" report, so this document starts there.

---

## 0. The rule that breaks people

| Where the value is read | When | Effect on the deployed site |
| --- | --- | --- |
| `.env`, `.env.local`, `process.env` on the **machine that runs `vite build`** | once, during `vite build` | replaces `import.meta.env.VITE_SUPABASE_URL` in the JS bundle with the literal value |
| Cloudflare Pages **runtime** variables (Workers/Functions `vars`), `wrangler.toml [vars]`, `.dev.vars` | per request, server-side | **none for this app** — there is no server code reading them |

This is a static SPA: there is no runtime configuration layer. A site built
without the two variables ships a bundle that literally contains

```js
const U = "" // or undefined
```

…no matter what is in your `.env` today. The fix is always *"make the variables
visible to the process that builds the bundle, then build again"*.

Verify that in one request against any deployment:

```sh
curl -s https://fatorati.tech/build-report.json
# {
#   "builtAt": "2026-10-13T19:18:36.732Z",
#   "source": "the Cloudflare Pages build environment",
#   "commit": "…",
#   "supabase": { "configured": true, "problemCode": null, "projectRef": "abcdefghijklmnop" }
# }
```

`configured: false` means **that** deployment was built without a usable pair —
no amount of editing `.env` locally will change it until a new build runs in the
right place. The file is generated by `vite.config.ts`
(`figmaSupabaseEnvPlugin`) and never contains a key.

## 1. Local development

```sh
cp .env.example .env
# fill VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY
pnpm dev
```

* **Restart required.** Vite reads `.env*` at startup; editing the file while
  the server runs changes nothing (HMR does not re-inline `import.meta.env`).
* `.env.local` **wins** over `.env`, `.env.development` wins over `.env` in
  `vite dev`, and `.env.production` wins over `.env` in `vite build`. Precedence
  (highest first): `.env.[mode].local` → `.env.[mode]` → `.env.local` → `.env` →
  real environment variables that are *missing* from a file are taken from
  `process.env`.
* Values are trimmed by the app, so stray spaces are fine — but surrounding
  **quotes are not**: `VITE_SUPABASE_URL="https://x.supabase.co"` is read with
  the quotes by a shell-exported variable, only stripped by dotenv-style files.
* Missing vs empty is the same thing to this app: `VITE_SUPABASE_URL=` (present
  but empty) is reported exactly like an unset variable.
* `pnpm dev` prints the verdict on every start:

  ```
  [supabase:dev] configured from the production mode environment … : https://<ref>.supabase.co (project <ref>)
  # or
  [supabase:dev] no usable Supabase configuration in … — full fix list follows
  ```

* Without a usable pair, the dev server offers **Continuer en mode local
  (développement)** on the login screen: a browser-local workspace with no
  Supabase account and no network call. It cannot exist in a production build
  (`import.meta.env.DEV` is replaced by `false`), by design.

## 2. GitHub Actions

The workflow (`.github/workflows/deploy.yml`) reads the variables from, in
order: repository **variables** (`vars.VITE_SUPABASE_URL`), then repository
**secrets** (`secrets.VITE_SUPABASE_URL`).

Repository → Settings → Secrets and variables → Actions:

* **Variables** tab: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (the anon key
  is public, it ships in the bundle — a variable is fine, a secret also works).
* **Secrets** tab: the same two names, plus `CLOUDFLARE_API_TOKEN` and
  `CLOUDFLARE_ACCOUNT_ID` **only if you want this workflow to deploy**.

Two behaviours worth knowing:

1. **On pull requests** (including Dependabot) a missing pair only produces a
   warning — a fork can legitimately have no secrets, and PRs must not fail for
   that reason.
2. **On `main`** the *Verify public build variables* step fails the job with an
   explicit message instead of quietly building an authentication-less site.
3. If `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` are absent, the deploy step
   is skipped and the workflow now says so in a `notice` annotation. That is the
   state this repository was in: every run passed, no run ever deployed, and
   production came from the Cloudflare Pages Git integration instead.

## 3. Cloudflare Pages (production) — the case that matters here

If the Pages project builds this repository itself, the variables must be set in
the **Pages project**, not in GitHub:

1. *Workers & Pages* → project `fatooralaw` → **Settings** →
   **Variables and secrets** → *Add* →
   * `VITE_SUPABASE_URL` = `https://<project-ref>.supabase.co` (plain text)
   * `VITE_SUPABASE_ANON_KEY` = `<anon/publishable key>` (encrypt it)
2. Add them **twice**: once with the **Production** environment selected, once
   with **Preview**. Preview deployments (`<branch>.fatooralaw.pages.dev`, PR
   previews) build with the Preview environment; adding the pair only to
   Production is the classic "works on the main domain, broken on preview".
3. **Redeploy.** Variables are read when a build starts — saving them does not
   rebuild. *Deployments* → ⋯ → *Retry deployment* (or push a commit), and use
   *Retry deployment* → uncheck *Use build cache* the first time, since the
   previous build's cache can hold the old, unconfigured bundle.
4. Watch the build log for the report line:

   ```
   [supabase:build] configured from the Cloudflare Pages build environment: https://<ref>.supabase.co (project <ref>)
   ```

   A Pages build with no usable pair now **fails** (visible in the deployment
   list) instead of publishing a broken site. `ALLOW_UNCONFIGURED_SUPABASE=1`
   as a Pages environment variable restores the old "build anyway" behaviour —
   only useful when you deliberately want the marketing pages without auth.

## 4. Deploying from your machine

```sh
export VITE_SUPABASE_URL="https://<ref>.supabase.co"
export VITE_SUPABASE_ANON_KEY="<anon key>"
pnpm build          # values are inlined here — the deploy does not need them
npx wrangler pages deploy dist --project-name=fatooralaw
```

`wrangler pages deploy` uploads `dist/`; it does **not** build it. Exporting the
variables only for the `wrangler` command is therefore useless — they must be
present for `pnpm build`.

## 5. The full failure matrix

| Symptom (login screen / console) | Cause | Fix |
| --- | --- | --- |
| "Ajoutez VITE_SUPABASE_URL et VITE_SUPABASE_ANON_KEY dans le fichier .env" | neither variable reached the build | set both in the environment that runs the build (§1–4) and rebuild |
| `missing-url` / `missing-key` | one of the two is empty | fill in the missing one; both are required |
| "les deux variables semblent inversées" | key pasted into the URL slot (or the reverse) | `VITE_SUPABASE_URL=https://<ref>.supabase.co`, key in the other slot |
| "contient l'adresse du tableau de bord Supabase" | `https://supabase.com/dashboard/...` pasted as the URL | use the **API URL**: `https://<ref>.supabase.co` (Project Settings → API) |
| "doit contenir l'URL de l'API du projet" | no scheme, or something that is not an http(s) URL | include `https://`; no trailing spaces |
| "Sécurité : … contient une clé secrète" | a `service_role` / `sb_secret_` key in a `VITE_*` variable | **rotate that key in Supabase** (it has been shipped to browsers), then put the anon/publishable key in the variable |
| Yellow warning "La clé appartient au projet X alors que l'URL pointe vers Y" | URL and key from two different projects | copy both from the *same* project |
| Banner absent, but sign-in returns "Invalid login credentials" | configuration is fine; wrong credentials or the account was never confirmed | check Supabase → Authentication → Users |
| Sign-in works on `.pages.dev` but not on `fatorati.tech` (or vice versa) | that environment has no variables / Supabase redirect URLs do not include the domain | add variables for both environments; allow the domain in Supabase → Authentication → URL configuration |
| Works in `pnpm dev`, broken in production | the build environment differs from your machine (§0) | set them where the build runs, rebuild, clear the build cache |
| Everything looks right but the browser still shows the old banner | the browser cached the previous JS bundle | hard reload, or verify with `/build-report.json` |

## 6. What is now enforced, and how to turn it off

| Behaviour | Where | Escape hatch |
| --- | --- | --- |
| Dev-server report at startup | `vite.config.ts` → `figmaSupabaseEnvPlugin` | — |
| Build report at startup + `dist/build-report.json` | same plugin | `ALLOW_UNCONFIGURED_SUPABASE=1` skips the file |
| **Failing** Cloudflare Pages build without a usable pair | same plugin (`CF_PAGES=1`) | `ALLOW_UNCONFIGURED_SUPABASE=1` |
| **Failing** any CI build on request | same plugin | `REQUIRE_SUPABASE_ENV=1` (opt-in), `ALLOW_UNCONFIGURED_SUPABASE=1` (opt-out) |
| Failed job on `main` when the variables are absent | `.github/workflows/deploy.yml` | run it on a PR (warning only), or set the variables |
| Banner + console warning in the browser | `src/lib/supabase.ts`, `src/components/SupabaseSetupNotice.tsx` | — |

The rules themselves live in `src/lib/supabaseConfig.ts` — the same module the
app uses at runtime, the build plugins use at build time, and
`tests/supabaseConfig.test.ts` pins. There is exactly one definition of "this
configuration is usable".
